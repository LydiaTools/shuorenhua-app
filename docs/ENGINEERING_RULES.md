# 「说人话」工程规则

这份规则把毕方 Desktop Harness 中与当前原生 Swift 产品真正相关的约束落到本项目，不引入 Rust、Tauri 或无业务价值的脚手架。

## 1. 架构边界

业务规则与宿主机制分离：

- `PromptBuilder.swift`、`CommitmentGuard.swift`、`PrototypeEngine.swift`、`ReplyMemory.swift` 与 `BridgeProtocol.swift` 承载平台无关或可独立测试的产品规则。
- `AccessibilityBridge.swift`、`QuickReplySender.swift`、`ClipboardModel.swift`、`DeepSeekService.swift` 与 `AIProvider.swift` 承载 macOS、网络、钥匙串或外部能力适配。
- `ContentView.swift` 与 `main.swift` 负责展示、交互和运行时装配，不复制承诺判断、行动拆解或回复规则。

如果界面层需要通过条件、重试或状态判断编排多个业务步骤，应先判断该编排是否属于稳定产品规则；属于产品规则时移入可独立测试的模块。

## 2. 产品安全与隐私

- 只处理用户本次主动提交的文本，不监听或积累剪贴板历史。
- 生成结果只能作为待确认草稿；目标输入框无法可靠确认时退化为复制，不自动发送。
- 回复不得新增原文或用户意图中不存在的时间、数量、价格、范围、责任或保证。
- 开发 Key 只允许保存在 macOS 钥匙串。源码、测试、日志和 Git 历史中不得出现真实 Key、Token、证书或公证凭据。
- 正式服务网关上线前，界面必须准确区分开发直连、效果预览和正式服务，不得把预览结果表示为线上成功。
- 用户原话、意图和回复样本只在功能确实需要且用户主动触发时发送；日志不得记录完整敏感正文。

## 3. 测试要求

- 每个产品行为变化至少覆盖核心成功路径和最高风险失败路径。
- 缺陷修复必须先有能复现问题的回归测试。
- 业务规则优先使用纯 Swift 测试，不依赖真实网络、当前剪贴板、用户主目录或现有聊天软件状态。
- Accessibility、输入框恢复、焦点变化、快捷键和发送边界需要真实宿主验证；仅有纯函数测试不能替代这类验证。
- 完整本地测试入口是 `./scripts/test.sh`。任一测试失败都不得形成新的交付包。

当前测试应持续覆盖：提示词与场景差异、桥接协议、回复目标判断、服务错误映射、承诺拦截、回复记忆及完整原型流程。

## 4. 版本与构建

- `Info.plist` 的 `CFBundleShortVersionString` 是当前用户版本唯一事实来源。
- `CFBundleVersion` 是构建号，必须为正整数；改变用户版本时同步决定是否提升构建号。
- 构建脚本从 `Info.plist` 读取版本并输出到 `build/v<version>/`，不得在脚本中复制版本常量。
- 当前构建目标是 Apple Silicon、macOS 13 及以上。未经真实构建与运行，不得声称支持 Intel、Windows 或其他平台。

## 5. 交付可信度

- 本地功能验证包可以使用 ad-hoc 签名，但必须明确标注，不得称为正式签名或已公证。
- 正式直接分发前必须完成 Developer ID Application 签名、Apple 公证和 stapling，并重新验证最终字节。
- 每个对外交付包都应记录版本、源码提交、目标平台/架构、SHA-256、签名状态、测试结果和未验证项。
- 改变安装包字节的重新签名、公证、压缩或替换资源都会形成新候选，需要重新计算摘要并复核。
- 公开下载仓库只放经批准的安装包、校验和和用户说明；私有源码仓库不自动触发公开发布。

## 6. 变更边界

- 普通实现只运行本次需要的测试，不自动增加重构、全仓治理或正式发布。
- 产品目标、付费边界、远程服务、数据收集、自动发送和跨平台迁移必须由负责人明确批准后再实施。
- 未经明确授权，不创建 GitHub Release、不修改公开仓库、不上传安装包，也不使用签名或生产凭据。
